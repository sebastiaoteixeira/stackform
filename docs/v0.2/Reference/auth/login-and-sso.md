title: "Login, SSO, and the token flow"
description: How password login and external SSO (OIDC, SAML) issue an app JWT, and how the generated app resolves credentials on each request.
---

This page ties together every way a principal obtains a token: built-in password
login, OIDC single sign-on, and SAML single sign-on. All three end the same way --
the app mints its own HS256 JWT and the caller presents it as a Bearer token on
subsequent requests.

Throughout this page the URLs assume:

```yaml
api:
  basePath: /api
  version: v1
```

so paths are `{basePath}/{version}/...` -> `/api/v1/...`. With `version` omitted,
drop the `/v1` segment.

## Enabling the login endpoints

Register and login are NOT generated by default. Turn them on with
`api.operations.auth`:

```yaml
api:
  basePath: /api
  version: v1
  operations:
    auth:
      register: true
      login: true
```

- `register` reuses the entity's `create` pipeline, so it accepts the same fields
  plus the implicit `password` (for password auth). Path: `POST /api/v1/{collection}/register`.
- `login` adds `POST /api/v1/{collection}/login`.

The examples below use a collection named `my-collection` (so URLs read
`/api/v1/my-collection/...`).

## Password login

```bash
curl -X POST http://localhost:8000/api/v1/my-collection/login \
  -H 'Content-Type: application/json' \
  -d '{"email": "alice@example.com", "password": "s3cr3t"}'
```

On success the response is the token plus the matched record:

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "id": "0190...",
    "email": "alice@example.com"
  }
}
```

The `user` object excludes `password`, `_id`, and the internal `_auth` namespace.
A wrong password or unknown identifier both return 401 with an indistinguishable
message (no user enumeration).

The generated FastAPI backend performs an exact repository lookup on the
declared identifier. Authentication does not depend on exposing a `list` CRUD
operation for the identity collection, so an auth entity may remain absent from
the application's ordinary collection routes.

## JWT claims

The minted token carries identity only:

```json
{
  "sub": "<primary key value>",
  "identity_collection": "<collection name>",
  "iat": 1700000000,
  "exp": 1700086400
}
```

- `sub` is the record's id-field value; access rules read it as `principal.sub`.
- `identity_collection` names which auth entity the principal belongs to.
- Roles are NOT in the token. On every request the app re-loads the record from
  its repository by the configured id field and re-reads its roles, so a role
  change takes effect on the next request without re-issuing a token.

Tokens are signed HS256 with `JWT_SECRET` and expire after `session.ttl` seconds,
or after `JWT_EXPIRATION_HOURS` (default 24) when `session.ttl` is unset. See
[Environment variables](../configuration/environment-variables.md).

## Credential resolution order

On each request the generated app resolves a principal by trying credentials in
this fixed order; the first that resolves a record wins:

1. `Authorization: Bearer <jwt>` -- a valid app JWT.
2. `X-API-Key: <key>` (or `Authorization: Bearer <key>`) -- matched against the
   top-level `apiKey` field of an apiKey auth entity.
3. `Authorization: Basic <base64(identifier:password)>` -- per-request password
   verification against a password auth entity.

In the generated FastAPI backend, each local credential path uses a single
exact repository lookup: id field for an app JWT, `apiKey` for an API key, and
the configured identifier for Basic or password login. It never depends on a
generated collection-list operation.

If none resolve, the request is unauthenticated and protected routes return 401.

## OIDC single sign-on

Attach an OIDC provider to the auth entity through a binding object in `auth.via`.
`discovery_url` is effectively required -- the app fetches the provider's
`.well-known/openid-configuration` from it at request time; there is no built-in
inference for "well-known" providers.

```yaml
providers:
  myoidc:
    type: oidc
    client_id: my-app
    client_secret: "${OIDC_CLIENT_SECRET}"
    discovery_url: "${OIDC_DISCOVERY_URL:-https://idp.example.com/.well-known/openid-configuration}"

entities:
  myEntity:
    type: auth
    auth:
      identifier: email
      via:
        - provider: password
        - provider: myoidc
          identifier: email
          claim_mapping:
            email: email
            name: name
          auto_provision: true
    fields:
      id: { type: id }
      email: { type: string, required: true, unique: true }
      name: { type: string }
```

`auto_provision` defaults to `true`. When a login succeeds at the IdP but no local
record matches, an `auto_provision: false` binding returns 403 ("User not found and
auto-provisioning is disabled") rather than creating a record.

The authorization-code flow:

```mermaid
sequenceDiagram
  participant B as Browser
  participant A as Generated app
  participant I as IdP
  B->>A: GET /api/v1/my-collection/auth/myoidc
  A->>A: fetch discovery_url (cached)
  A-->>B: 302 to authorization_endpoint (response_type=code)
  B->>I: follow redirect, authenticate
  I-->>B: 302 to /api/v1/my-collection/auth/myoidc/callback?code=...
  B->>A: GET callback with code
  A->>I: POST token_endpoint (code, client_id, client_secret)
  I-->>A: access_token
  A->>I: GET userinfo_endpoint (Bearer access_token)
  I-->>A: claims
  A->>A: map claims, find-or-provision record, issue one-time login code
  A-->>B: 302 to FRONTEND_URL/auth/callback?code=<code>
  B->>A: POST /api/v1/auth/exchange {code}
  A->>A: redeem code (single-use), mint app JWT
  A-->>B: 200 {token}
```

Notes on the callback:

- Claims are copied into the new or matched record only for keys present in
  `claim_mapping`, converted to the field's type. A claim absent from the IdP
  response is omitted (not set to null). Every sign-in brings a matched record's
  mapped fields up to date.
- If `claim_mapping` does not fill the binding's `identifier`, the app falls back to
  the `email`, then `login`, then `sub` claim for the identifier value. Claims that
  yield no usable identifier return 401.
- A provisioned record gets a server-generated id.
- Token exchange failure, userinfo failure, an expired token, or a sign-in that
  would duplicate a unique value each return 401. A callback whose `state` does
  not match the login that started it returns 400 (`Invalid OIDC state`).
- The app JWT never travels in a redirect URL. The callback instead mints a
  single-use login code and redirects to `{FRONTEND_URL}/auth/callback?code=<code>`.
  If `FRONTEND_URL` is unset, the app's own base URL is used. The React login page
  reads the `code` query parameter and `POST`s it to `/api/v1/auth/exchange` as
  `{"code": "<code>"}`, receiving `{"token": "<jwt>"}` in return.
- The login code is stored in an `_oidc_login_codes` collection in the identity
  collection's datastore (Mongo or SQL), lives for 60 seconds, and is redeemed
  atomically (delete-on-read), so a code works exactly once even across workers.
  A missing code returns 400 (`Missing code`); an unknown or expired code returns
  401 (`Invalid or expired code`).

### Password login inset

Password login is the non-redirect counterpart of the OIDC flow: instead of bouncing
through an IdP, the browser (or any client) posts credentials directly and receives
the same shaped `{token, user}` JSON.

```mermaid
sequenceDiagram
  participant C as Client
  participant A as Generated app
  C->>A: POST /api/v1/users/login {identifier, password}
  A->>A: verify password (PBKDF2), mint app JWT
  A-->>C: 200 {token, user}
```

### GitHub special case

GitHub does not implement OIDC. When the provider name is `github`, the app skips
the discovery `userinfo_endpoint` and fetches the profile from
`https://api.github.com/user` using the access token. Everything else (claim
mapping, provisioning, JWT minting, redirect) is identical.

## SAML single sign-on

A SAML provider needs `idp_metadata_url` and `sp_entity_id`:

```yaml
providers:
  mysaml:
    type: saml
    idp_metadata_url: "${SAML_METADATA_URL}"
    sp_entity_id: my-app

entities:
  user:
    type: auth
    auth:
      identifier: email
      via:
        - provider: password
        - provider: mysaml
          identifier: email
          claim_mapping:
            email: email
          auto_provision: true
    fields:
      id: { type: id }
      email: { type: string, required: true, unique: true }
```

SAML routes (all under `/api/v1/{collection}/auth/{provider}`):

| Method | Path | Description |
|--------|------|-------------|
| GET | `.../auth/{provider}` | Begin login; 302 to the IdP. |
| POST | `.../auth/{provider}/callback` | Assertion Consumer Service. 303 to `{FRONTEND_URL}/auth/callback?code=<code>`. |
| GET | `.../auth/{provider}/metadata` | Service-provider metadata XML. |
| GET | `.../auth/{provider}/logout` | Redirect to the IdP's single logout service. |

The ACS callback ends like the OIDC callback: it mints a single-use login code and
redirects to the frontend, which redeems the code at `/api/v1/auth/exchange`. A
missing or malformed `SAMLResponse` returns 400; a failed assertion, a response
that answers no pending login, or a replayed assertion returns 401;
`auto_provision: false` with no matching record returns 403. The identifier falls
back to the SAML NameID when `claim_mapping` does not supply it. IdP metadata is
fetched at request time from `idp_metadata_url`. See
[SAML provider](../providers/saml.md).

## Listing configured providers

When an entity binds one or more external providers, the app also exposes:

```
GET /api/v1/{collection}/auth/providers
```

It returns a list of `{name, type}` objects (for example
`[{"name": "myoidc", "type": "oidc"}]`). The generated React login page calls this
endpoint to render one SSO button per provider, alongside the password login form.

## Environment variables

| Variable | Used by | Purpose |
|----------|---------|---------|
| `JWT_SECRET` | all login paths | HS256 signing secret. Set a strong value in production. |
| `JWT_EXPIRATION_HOURS` | all login paths | Token lifetime in hours when `session.ttl` is unset (default 24). |
| `PASSWORD_HASH_ROUNDS` | password register/login | PBKDF2 iteration count (default 390000). |
| `FRONTEND_URL` | OIDC and SAML callbacks | Base for the `.../auth/callback?code=` redirect. |
| `<PROVIDER>_CLIENT_SECRET` | OIDC token exchange | Each confidential provider's client secret (e.g. `KEYCLOAK_CLIENT_SECRET`), a `SecretStr` setting read at run time. Emitted only when the provider declares a `client_secret`. |

Provider `${VAR}` placeholders are interpolated from the environment at build time
and baked into the output -- except `client_secret`, which is deferred to runtime. A
confidential provider's secret is read at run time from `<PROVIDER>_CLIENT_SECRET`
(e.g. `KEYCLOAK_CLIENT_SECRET`) via a `SecretStr` setting, so the literal must never
be placed in the spec. See [Environment variables](../configuration/environment-variables.md).

`client_secret` is optional: omit it for a public client and the token exchange runs
without one. See [OIDC provider](../providers/oidc.md#fields).
