---
title: "Repository Operations"
description: "How a repository selects its CRUD subset with crud:, and how custom query/handler operations are declared."
---

A repository exposes two kinds of operations:

- The six built-in CRUD operations, selected with the `crud:` list.
- Custom operations under `operations:`, each backed by a MongoDB `query:` command or a `handler:` import path.

## Built-in CRUD operations

| Operation | HTTP   | Description |
|-----------|--------|-------------|
| `list`    | GET    | List documents in the collection. |
| `get`     | GET    | Retrieve one document by primary key. |
| `create`  | POST   | Insert a new document. The id field is server-generated by default. |
| `update`  | PATCH  | Partial update. Only supplied fields are modified. |
| `replace` | PUT    | Full replacement of a document. |
| `delete`  | DELETE | Remove a document by primary key. |

All six default to enabled, including `replace`. A repository that omits `crud:` exposes the full set:

```yaml
repositories:
  myCollection:
    entity: myEntity
    # crud omitted -> all six operations enabled
```

## Selecting a subset with `crud:`

List the operations a repository should expose. Anything not listed is removed end to end (see [Composable per-operation CRUD](composable-crud.md)):

```yaml
repositories:
  myCollection:
    entity: myEntity
    crud: [create, list, get, delete]   # no update -> no PATCH route, no Edit action
```

Operation names must be among `list`, `get`, `create`, `update`, `replace`, `delete`. An unknown name is reported as `CRUD_OPERATION_INVALID`. A repository that sets `crud:` but declares no `entity:` is reported as `CRUD_WITHOUT_ENTITY`.

## Disabling `replace` (or any op) globally

To turn an operation off across every repository that does not list `crud:` explicitly, set the flag under `api.operations.defaults`. The defaults block exists to disable operations; everything is on otherwise:

```yaml
api:
  basePath: /api
  version: v1
  operations:
    defaults:
      replace: false   # PUT off everywhere a repo omits crud:
```

A repository's `crud:` list always overrides these defaults for that repository.

## Resolution precedence

For each operation, the final on/off decision is resolved in this order (highest wins):

1. The service's `operations.<op>` override (`services.<name>.operations`).
2. The repository's `crud:` list.
3. `api.operations.defaults`.
4. All operations enabled.

The per-operation override lives on the service, not the repository. It accepts `true`, `false`, or `{ handler: <dotted.path> }`:

```yaml
services:
  myCollection:
    repository: myCollection
    operations:
      delete: false                          # drop delete from this service only
      replace: { handler: my_app.replace }   # back this op with a custom handler
```

## Custom operations

Custom operations are declared under `repositories.<name>.operations`. Each entry needs either a `query:` (a MongoDB command) or a `handler:` (a dotted import path). An entry with neither is reported as `OPERATION_MISSING_QUERY_OR_HANDLER`.

### Query-backed operations

A `query:` runs a named MongoDB command against the repository's collection. The command must be one of the supported names, and most commands require a specific argument field:

```yaml
repositories:
  myCollection:
    entity: myEntity
    operations:
      published:
        query:
          command: find
          filter: { status: published }
      count-all:
        query:
          command: countDocuments
          filter: {}
```

Supported commands and their required field:

| Required field | Commands |
|----------------|----------|
| `filter`       | `find`, `findOne`, `countDocuments`, `distinct`, `deleteOne`, `deleteMany`, `updateOne`, `updateMany`, `replaceOne`, `findOneAndUpdate`, `findOneAndReplace`, `findOneAndDelete` |
| `pipeline`     | `aggregate` |
| `document`     | `insertOne` |
| `documents`    | `insertMany` |
| `requests`     | `bulkWrite` |
| (none)         | `estimatedDocumentCount` |

An unknown command is reported as `QUERY_COMMAND_UNKNOWN`; a missing required field as `QUERY_MISSING_FIELD`.

By default the query targets the repository's entity collection. Override the target with `query.collection`:

```yaml
repositories:
  myCollection:
    entity: myEntity
    operations:
      recent-related:
        query:
          command: find
          filter: {}
          collection: my-other-collection   # query a different collection
```

A repository with no `entity:` can still declare query operations, but each query must then supply a `collection:`. Omitting both is reported as `QUERY_MISSING_COLLECTION`.

### Handler-backed operations

For logic that a single MongoDB command cannot express, point `handler:` at an async function. The generated repository imports it and calls it as `await handler(**kwargs)`, where the keyword arguments come from the caller:

```yaml
repositories:
  myCollection:
    entity: myEntity
    operations:
      archive-stale:
        handler: my_app.archive_stale
```

A repository that declares no `entity:` and no `operations:` is reported as `REPOSITORY_EMPTY`.

## Relationship to services

A service binds a service name to one repository operation by name. The `operation` may be a built-in CRUD op or a custom operation declared above:

```yaml
services:
  list-items: { repository: myCollection, operation: list }
  published:  { repository: myCollection, operation: published }
```

The minified form `{ repository: myCollection }` expands to one service per resolved CRUD operation; the per-operation overrides described above apply during that expansion. A custom operation only becomes reachable over HTTP once a controller route names the service backing it.
