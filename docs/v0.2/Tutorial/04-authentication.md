**Concept introduced:** Auth entities with password-based login and register endpoints, the credentials a client can present, and the fact that routes are protected by default once an identity entity exists.

## Adding a user entity with password auth

Mark an entity with `type: auth` and add an `auth:` block to make it an identity provider.

The `identifier` field tells the engine which field uniquely identifies a user at login time. In this example, `identifier: email` means the user logs in with their email address.

The `via` field tells the engine how the user proves their identity. `via: password` means username/password authentication. The engine treats `password` as an implicit input on register -- you do not declare it in `fields:`. The password is hashed before storage and never persisted in plain text.

Register and login routes are NOT generated by default. Enable them explicitly with `api.operations.auth: { register: true, login: true }`.

```yaml
version: "0.2"

api:
  basePath: /api
  version: v1
  operations:
    auth:
      register: true
      login: true

mongo:
  uri: mongodb://localhost:27017
  database: yaml_api

entities:
  user:
    type: auth
    auth:
      identifier: email
      via: password
    fields:
      id: { type: id }
      email: { type: string, required: true, unique: true }
      displayName: { type: string, required: true }

  author:
    fields:
      id: { type: id }
      name: { type: string, required: true }
      bio: { type: string }

  note:
    fields:
      id: { type: id }
      title: { type: string, required: true }
      body: { type: string }
      authorId: { type: ref, ref: author }

repositories:
  users:
    entity: user
  authors:
    entity: author
  notes:
    entity: note

services:
  users: {}
  authors: {}
  notes: {}

controllers:
  users:
    service: users
    base_path: /users
    access: public
    operations:
      register: { access: public }
      login: { access: public }

  authors:
    service: authors
    base_path: /authors
    access: public

  notes:
    service: notes
    base_path: /notes
    access: public
```

With `api.basePath: /api` and `api.version: v1`, every route is prefixed with `/api/v1`. The `api:` block above is shown in full so you can reproduce the exact URLs used in this tutorial.

## How password auth works

When an entity uses `via: password`, the engine accepts a `password` field on the register payload. You do not declare it in `fields:` -- it is implicit. Declaring it yourself is rejected at build time:

- A `password` field raises `AUTH_PASSWORD_FIELD_FORBIDDEN`.
- A `passwordHash` field raises `AUTH_PASSWORD_HASH_FIELD_FORBIDDEN`.

The engine hashes the password with PBKDF2-SHA256 and stores it in the per-document `_auth` namespace as `_auth.passwordHash`; the raw password is never persisted. The stored value has the format `pbkdf2$sha256$<rounds>$<salt>$<hash>`. The `_auth` namespace and the password are stripped from every response.

A JWT (JSON Web Token) is a signed string that encodes the user's identity. The token carries only `sub` (the user's id), `identity_collection` (the source collection name), `iat`, and `exp` -- it does NOT carry roles. The user record (and any roles) is loaded from MongoDB on each request, so role changes apply immediately. After login, present the token in the `Authorization: Bearer <token>` header on subsequent requests. Access control using the token is covered in [Tutorial 05: Access Control](./05-access-control.md).

## Routes are protected by default

As soon as any `type: auth` entity exists in the spec, every route that is not explicitly `access: public` requires a valid principal (a resolved, authenticated user). A request without valid credentials to a protected route gets `401 Unauthorized`. This is why the controllers above set `access: public` on the routes that should stay open (including `register` and `login`).

A minified controller (one declared with a bare `service:` and no `access:`) defaults to `access: public`. To protect a resource you must opt in with `access: "*"` (or a more specific rule). Locking down routes is the subject of [Tutorial 05: Access Control](./05-access-control.md).

Note: if a spec has no `type: auth` entity at all, there is no identity collection to authenticate against, so non-public routes are left open. Protection is wired only when an auth entity exists.

## Generated auth endpoints

| Method | Path | Description |
|--------|------|-------------|
| POST | /api/v1/users/register | Create a new user (password hashed automatically) |
| POST | /api/v1/users/login | Authenticate and receive a JWT token |

Standard CRUD endpoints are also generated for `/api/v1/users`.

## Register and login

```bash
# Register
curl -X POST http://127.0.0.1:8000/api/v1/users/register \
  -H 'Content-Type: application/json' \
  -d '{"email": "alice@example.com", "displayName": "Alice", "password": "s3cr3t"}'

# Login
curl -X POST http://127.0.0.1:8000/api/v1/users/login \
  -H 'Content-Type: application/json' \
  -d '{"email": "alice@example.com", "password": "s3cr3t"}'
```

A successful login returns the token plus the user record, with `password`, `_id`, and the `_auth` namespace stripped:

```json
{
  "token": "eyJ...",
  "user": {
    "id": "0192...",
    "email": "alice@example.com",
    "displayName": "Alice"
  }
}
```

## Presenting credentials

The generated backend resolves a request's principal by trying these credential sources in order:

1. Bearer JWT -- `Authorization: Bearer <token>` (the token returned by `/login`).
2. API key -- `X-API-Key: <key>` or `Authorization: Bearer <key>` (for `via: apiKey` entities; see the auth reference).
3. HTTP Basic -- `Authorization: Basic <base64(identifier:password)>`, validated against the stored password hash on every request.

```bash
# Bearer JWT (after login)
curl http://127.0.0.1:8000/api/v1/notes \
  -H "Authorization: Bearer eyJ..."

# HTTP Basic (identifier:password, base64-encoded)
curl http://127.0.0.1:8000/api/v1/notes \
  -u 'alice@example.com:s3cr3t'
```

## Authentication environment variables

The generated backend reads these at runtime:

| Variable | Default | Purpose |
|----------|---------|---------|
| JWT_SECRET | yaml-api-dev-secret-change-me | HS256 signing secret for JWTs |
| JWT_EXPIRATION_HOURS | 24 | Token lifetime in hours |
| PASSWORD_HASH_ROUNDS | 390000 | PBKDF2-SHA256 iteration count |

**Watch out:** The default `JWT_SECRET` is an insecure placeholder. Always set `JWT_SECRET` to a strong random value before deploying to production.

## Key points

- `type: auth` on an entity enables identity provider behavior.
- The `auth:` block configures authentication. `via: password` enables username/password auth.
- `identifier: email` sets which field is used as the login username.
- Register and login routes are off by default; enable them with `api.operations.auth: { register: true, login: true }`.
- Passwords are hashed with PBKDF2-SHA256 and stored at `_auth.passwordHash`. The raw password is never stored, and `_auth` is stripped from responses.
- The `password` field on register is implicit -- declaring `password` or `passwordHash` in `fields:` is a build error.
- Login returns `{"token": "...", "user": {...}}`; the JWT carries identity only (`sub`, `identity_collection`), and roles are read from the user record per request.
- A client can authenticate with a Bearer JWT, an API key, or HTTP Basic credentials.
- Once an auth entity exists, every non-public route requires a valid principal (401 otherwise).
