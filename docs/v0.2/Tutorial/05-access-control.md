**Concept introduced:** Controller-level and per-operation `access:` rules: `public`, `"*"` (any authenticated principal), `<entity>:*` scoping, and per-operation overrides.

> **Enforcement status**
>
> Roles (exact match), `<entity>:*` scoping, and ownership/ABAC `when` rules
> are enforced by the generated FastAPI backend, the generated DRF backend, and the
> `yaml-api run` dev server alike. A request that fails a rule gets 401 (missing or
> invalid credentials), 403 (authenticated but not allowed), or 404 (record not
> found, checked before ownership). Two current limitations: role hierarchy (for
> example `admin` inheriting `moderator`) is accepted in YAML but not yet applied
> during enforcement -- only exact role matches are checked; and conditional or
> ownership rules require a v0.2 spec, because v0.1 specs do not parse `when` rules.

## Restricting write operations

With a user entity in place, restrict note creation, update, replace, and delete to
authenticated users only, while keeping reads public.

The `api:` block below sets `basePath: /api` and `version: v1`, so every route is
served under `/api/v1/...`. The `operations.auth` block is required to generate the
`register` and `login` endpoints; they are off by default.

```yaml
version: "0.2"

api:
  basePath: /api
  version: v1
  operations:
    auth:
      register: true
      login: true

mongo:
  uri: mongodb://localhost:27017
  database: myapp

entities:
  user:
    type: auth
    auth:
      identifier: email
      via: password
    fields:
      id: { type: id }
      email: { type: string, required: true, unique: true }
      displayName: { type: string, required: true }

  note:
    fields:
      id: { type: id }
      title: { type: string, required: true }
      body: { type: string }

repositories:
  users:
    entity: user
  notes:
    entity: note

services:
  users: {}
  notes: {}

controllers:
  users:
    service: users
    base_path: /users
    access: "*"
    operations:
      register: { access: public }
      login: { access: public }

  notes:
    service: notes
    base_path: /notes
    access: public
    operations:
      create: { access: "*" }
      update: { access: "*" }
      replace: { access: "*" }
      delete: { access: "*" }
```

> **Watch out: minified controllers default to `public`.** A controller written in
> the minified `service:` form (like the two above) treats a missing `access:` as
> `public`. If you omit `access:` on the `users` controller, its `list`/`get`/`update`/
> `replace`/`delete` routes are world-readable and world-writable. Set
> `access: "*"` (as shown) to lock the whole controller down, then re-open
> `register` and `login` per-operation.

All six CRUD operations are generated by default, including `replace` (PUT). If you
do not override `replace` here it inherits the controller default (`public`), so the
example overrides it alongside `create`, `update`, and `delete`.

## How access resolution works

The controller-level `access:` is the default for all operations. A per-operation
`access:` under `operations.<op>` overrides the default for that operation only.

| Operation | Effective access | Who can call it |
|-----------|-----------------|-----------------|
| list | public | anyone |
| get | public | anyone |
| create | `"*"` | any authenticated user |
| update | `"*"` | any authenticated user |
| replace | `"*"` | any authenticated user |
| delete | `"*"` | any authenticated user |

**Authentication is required by default.** Once any `type: auth` entity exists in the
spec, every non-public route requires a valid principal. Only a literal
`access: public` opts a route out. With no auth entity in the spec, nothing is
protected even when `access:` is set, because there is no identity collection to
authenticate against.

## Calling a protected route

The URLs below use the `/api/v1` prefix from the `api:` block above.

**Note:** This example uses `jq` to extract the token from the JSON response. If you
don't have `jq` installed, copy the token value manually from the JSON output.

```bash
# Get a token first. Login returns {"token": "...", "user": {...}};
# the user object has password, _id, and _auth stripped out.
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/v1/users/login \
  -H 'Content-Type: application/json' \
  -d '{"email": "alice@example.com", "password": "s3cr3t"}' \
  | jq -r .token)

# Create a note with the token
curl -X POST http://127.0.0.1:8000/api/v1/notes \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"title": "Protected note"}'
```

A request to a protected route with no credentials (or an invalid/expired token)
returns 401. A request with a valid token that does not satisfy the rule returns 403.

You can also authenticate per-request with HTTP Basic instead of a token:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/notes \
  -u 'alice@example.com:s3cr3t' \
  -H 'Content-Type: application/json' \
  -d '{"title": "Protected note"}'
```

## Access values

| Value | Meaning |
|-------|---------|
| `public` | No authentication required |
| `"*"` | Any authenticated principal (any auth entity) |
| `user:*` | Any principal from the `user` entity specifically |
| `user:admin` | User with the `admin` role (requires roles, covered in tutorial 06) |

With only one auth entity, `user:*` and `"*"` are
equivalent. The distinction matters once you have multiple auth entities (for example
users and API clients): `user:*` admits only the `user`
collection, while `"*"` admits any authenticated principal.

**Note:** Per-operation `access:` completely replaces the controller-level default.
There is no merging. If the controller has `access: public` and an operation has
`access: "*"`, only `"*"` applies to that operation.

## Disabling an operation

Setting an operation to `false` removes its route entirely. For example, to forbid
deleting notes at all:

```yaml
controllers:
  notes:
    service: notes
    base_path: /notes
    access: public
    operations:
      create: { access: "*" }
      update: { access: "*" }
      replace: { access: "*" }
      delete: false
```

There is no `DELETE /api/v1/notes/{id}` route in the generated app, no service method,
and no Delete button in any generated UI. See the repositories reference for selecting
the CRUD subset at the data layer with a `crud:` list.
