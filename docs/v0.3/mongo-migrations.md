# MongoDB migrations

`yaml-api migrate` manages versioned schema evolution for both relational and
MongoDB datastores through one command tree. The subcommands are identical
across backends; the driver is selected from the datastore kind, so nothing new
has to be learned to migrate a document store.

```
yaml-api migrate new     spec.yaml [-m MESSAGE] [--datastore NAME]
yaml-api migrate up      spec.yaml [--to REVISION] [--datastore NAME]
yaml-api migrate down    spec.yaml [--to REVISION] [--datastore NAME]
yaml-api migrate status  spec.yaml [--datastore NAME]
yaml-api migrate history spec.yaml [--datastore NAME]
```

## Choosing the datastore

When a spec declares a single datastore it is selected automatically. With more
than one, pass `--datastore NAME`. A spec that mixes a relational and a MongoDB
datastore keeps the relational Alembic default when no datastore is named; name
the MongoDB datastore explicitly to migrate it.

## Revisions

Revisions are ordered JSON files under `mongo_migrations/<datastore>/`, each
linked to its predecessor through `down_revision`, mirroring the Alembic version
chain. A revision is a list of operations applied forward on `up` and reversed on
`down`:

- `create_index` / `drop_index` — index and unique-constraint changes. These are
  autogenerated by `migrate new` from the spec's `unique: true` fields (the same
  indexes materialized on connect when a spec is not yet under migrations), and
  each is reversible.
- `run_handler` — the escape hatch for data migrations Mongo cannot express
  declaratively (backfills, field renames, collection reshapes). It names a
  dotted-path async handler called with the datastore handle:

  ```json
  {
    "revision": "0002",
    "down_revision": "0001",
    "message": "backfill display names",
    "operations": [
      { "op": "run_handler", "up": "my_app.migrations.backfill", "down": "my_app.migrations.undo_backfill" }
    ]
  }
  ```

  ```python
  async def backfill(db):
      async for user in db["users"].find({"display_name": None}):
          await db["users"].update_one({"_id": user["_id"]}, {"$set": {"display_name": user["email"]}})
  ```

  Provide `down` for a reversible data migration; omit it for a one-way step.

## Applied history

The applied revisions are persisted in the datastore itself, in a `migrations`
collection — the document-store analogue of Alembic's version table. `status`
prints the current head from it and `history` lists the revision chain on disk.

## Graduation and baseline stamping

Outside of migrations, a MongoDB spec materializes its unique indexes on connect.
Once a `mongo_migrations/` tree exists the spec graduates: on-connect index
creation is disabled and schema evolution flows only through `migrate`.

The first `migrate new` on a datastore whose collections and indexes already
exist stamps that revision as the baseline — recording it as applied without
re-running its operations — so an existing deployment adopts migrations without
rebuilding what is already there.
