`yaml-api migrate` manages versioned schema evolution for both relational and
MongoDB datastores through one command tree. The subcommands are identical
across backends; the driver is selected from the datastore kind, so nothing new
has to be learned to migrate a document store.

```
yaml-api migrate new     spec.yaml [-m MESSAGE] [--datastore NAME]
yaml-api migrate up      spec.yaml [--to REVISION] [--datastore NAME]
yaml-api migrate down    spec.yaml [--to REVISION] [--datastore NAME]
yaml-api migrate status  spec.yaml [--datastore NAME]
yaml-api migrate history spec.yaml [--datastore NAME]
```

## Choosing the datastore

When a spec declares a single datastore it is selected automatically. With more
than one, pass `--datastore NAME`. A spec that mixes a relational and a MongoDB
datastore keeps the relational Alembic default when no datastore is named; name
the MongoDB datastore explicitly to migrate it.

## Revisions

Revisions are JSON files under `mongo_migrations/<datastore>/`, each linked to
its predecessor through `down_revision`, mirroring the Alembic version chain.
The chain — not the filename — defines the order: every file in the directory is
read, and the revisions are sorted by following `down_revision` from the base.
A duplicate id, two revisions claiming the same predecessor, or a revision that
does not lead back to the base is reported as an error instead of being applied
in an arbitrary order.

`migrate new` writes `NNNN_<message-slug>_<id>.json`, where `NNNN` is the
position in the chain at the time of writing and `<id>` is a random 12-character
hex id, so two people adding a revision in parallel never collide on the id.

A revision is a list of operations applied in order on `up` and in reverse on
`down`:

- `create_index` / `drop_index` — index and unique-constraint changes. These are
  autogenerated by `migrate new`, which diffs the spec's `unique: true` fields
  against the indexes the existing chain already accounts for: fields the chain
  does not yet cover become `create_index`, indexes the spec no longer declares
  become `drop_index`. Each is reversible — `up` creates what `down` drops.
- `run_handler` — the escape hatch for data migrations Mongo cannot express
  declaratively (backfills, field renames, collection reshapes). It names a
  dotted-path async handler called with the datastore handle:

  ```json
  {
    "revision": "8f2c41ab90d7",
    "down_revision": "1b70c3d95ee4",
    "message": "backfill display names",
    "operations": [
      { "op": "run_handler", "up": "my_app.migrations.backfill", "down": "my_app.migrations.undo_backfill" }
    ]
  }
  ```

  ```python
  async def backfill(db):
      async for user in db["users"].find({"display_name": None}):
          await db["users"].update_one({"_id": user["_id"]}, {"$set": {"display_name": user["email"]}})
  ```

  Provide `down` for a reversible data migration; omit it for a one-way step —
  a `down` that reaches a revision with no `down` handler fails rather than
  silently skipping the step.

  The dotted path resolves against the installed environment and against the
  directory holding the spec, the way `yaml-api run` resolves service handlers,
  so a `handlers.py` next to the spec is named `handlers.backfill`. A path that
  cannot be imported, or that names something which is not callable, stops the
  run and names the revision.

  The runner imports the dotted path and calls it, so a revision file is
  executable code by reference. Revision files and the modules they name are
  trusted source: review them as you review application code, and never apply a
  revision tree you would not run as a program.

The whole tree is read and checked before any revision is applied: a file that is
not JSON, that carries keys this format does not define, that declares an
operation other than the three above, or that declares an index operation
without its `collection` and `field`, is reported by name and the datastore is
left untouched.

## Targets

`--to` accepts the terminal for the direction (`head` for `up`, `base` for
`down`), a relative step count in that direction (`+N` on `up`, `-N` on `down`),
or the id of a revision already in the chain. Anything else is rejected. On
`up`, a revision id is applied through that revision inclusive; on `down`, the
named revision is the floor and is left applied.

```bash
yaml-api migrate up   my-spec.yaml --to +1
yaml-api migrate down my-spec.yaml --to -1
yaml-api migrate down my-spec.yaml --to base
```

## Applied history

The applied revisions are persisted in the datastore itself, in a `migrations`
collection — the document-store analogue of Alembic's version table. Each
document is keyed by the revision id and carries a state: `running` while its
operations are in flight, `applied` once they have all succeeded.

That name is therefore reserved: a spec whose MongoDB datastore already holds a
repository named `migrations` is refused by every `migrate` subcommand, rather
than having its documents read as revision history. Rename the repository or
move it to another datastore.

A revision is claimed by inserting that document before any operation runs, so
the unique `_id` makes the claim atomic: two `migrate up` processes racing on the
same datastore cannot both apply the same revision. Reverting claims the same
way, moving `applied` back to `running` before the reversal starts.

A revision left in `running` was interrupted — the process died partway through,
so part of it may already be applied. `up` and `down` both refuse to proceed
while one exists. Recovery is forward-only and manual: finish or undo that
revision's operations by hand, delete its document from the `migrations`
collection, then re-run.

`status` prints the current revision, the pending ones, and — when present — the
interrupted revisions and any recorded revision whose file is missing from the
tree. `history` lists the chain newest first, each line showing
`down_revision -> revision: message [state]`, where the state is `applied`,
`running`, or `pending`.

## Graduation and baseline stamping

Outside of migrations, a MongoDB spec materializes its `unique: true` fields as
indexes when the datastore is connected. Graduation is per datastore family: a
`mongo_migrations/` tree graduates the spec's MongoDB datastores, and a
relational `migrations/` tree graduates its relational ones, so adopting Alembic
never silences MongoDB index creation and adopting MongoDB migrations never
silences relational `create_all`.

Where MongoDB graduation takes effect:

| Runtime | On-connect unique-index creation |
| --- | --- |
| `yaml-api run` (development server, FastAPI and `--raw` ASGI) | Runs when no `mongo_migrations/` sits next to the spec; skipped once it does. |
| Generated FastAPI backend | Emitted only when `mongo_migrations/` was absent at generation time; a graduated spec generates an app whose startup makes no index-creation call. |
| Generated DRF backend | Never runs, graduated or not: the target emits an `initialize_indexes` helper but no startup path calls it, so its indexes come from `migrate` (or by hand) in every case. |
| Generated raw ASGI backend | Never runs, for the same reason as DRF. |

The generated FastAPI decision is made at generation time by looking for
`mongo_migrations/` next to the spec, and baked into the emitted `app.py`; the
generated app never looks for a migrations tree at run time. Regenerate the
project after the first `migrate new` for graduation to reach an
already-generated backend.

Graduation governs MongoDB index creation only. The generated FastAPI backend
still calls SQLAlchemy `create_all` on connect for relational datastores whether
or not `migrations/` exists; `yaml-api run` is the only runtime that honours
relational graduation today.

Baseline stamping covers the datastore that already has the schema. When the
first `migrate up` finds an empty `migrations` collection and the spec's
collections and unique indexes already present in the datastore, it records the
first revision as applied without running its operations, then continues with
the rest of the chain. An existing deployment therefore adopts migrations
without rebuilding what is already there.
